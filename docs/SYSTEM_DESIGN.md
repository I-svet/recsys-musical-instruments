# Системный дизайн воспроизводимого сравнения рекомендательных моделей

Дата: 19 октября 2026 года.
Статус: реализованы подготовка данных, пять моделей, оценка, подбор параметров и отчёт. Результаты основного эксперимента публикуются в [reports/REPORT.md](../reports/REPORT.md).

## 1. Решение

Строим локальный пакет Python с командным интерфейсом и файловыми артефактами. Один конвейер готовит данные, обучает пять независимо реализованных моделей, формирует персональные top-10 и вычисляет метрики по единому протоколу.

Основные модели:

1. ItemKNN с косинусным сходством и сглаживанием.
2. Explicit ALS со смещениями пользователя и объекта.
3. EASE.
4. FM второго порядка с историческими и календарными метапризнаками.
5. timeSVD++ с временными компонентами и причинно корректной историей.

MostPopular добавляется как контрольный baseline сверх обязательных пяти. SVD++ без временных компонент и FM только с ID нужны как небольшие абляционные эксперименты.

Ключевые решения проекта:

- Источник: полный ratings-only файл категории; активная подвыборка определяется только по train.
- Глобальные временные границы и фиксированный каталог.
- Одна рекомендация на пользователя в начале оцениваемого периода.
- Полное ранжирование каталога без сэмплирования негативов при оценке.
- Основная метрика выбора конфигурации: macro NDCG@10.
- Настройка на validation, финальное переобучение на train + validation, один фиксированный test.
- В GitHub публикуются код, инструкции, конфигурации и результаты. Raw-данные и крупные параметры моделей не включаются в Git.

Веб-приложение, API-сервис, внешняя база данных, очередь задач, feature store и отдельный сервер экспериментов не нужны для этой работы. Если позже потребуется демо, оно будет тонким клиентом к тому же сохранённому model artifact и RecommendationEngine.

## 3. Данные и их происхождение

Источники:

- [Официальная страница Amazon 2018](https://cseweb.ucsd.edu/~jmcauley/datasets/amazon_v2/).
- [Musical_Instruments.csv](https://mcauleylab.ucsd.edu/public_datasets/data/amazon_v2/categoryFilesSmall/Musical_Instruments.csv).
- [Метаданные категории](https://mcauleylab.ucsd.edu/public_datasets/data/amazon_v2/metaFiles2/meta_Musical_Instruments.json.gz).

Не нужны тексты отзывов, reviewerName, изображения покупателей и сами изображения товаров. CSV достаточен для обучения; метаданные дают читаемые подписи рекомендаций и отдельный дополнительный эксперимент.

Raw-файлы неизменяемы. Загрузчик проверяет SHA256, пишет через временный файл и завершает операцию атомарным переименованием. Изменение файла по тому же URL требует нового manifest и новой версии benchmark.

Схема исходного события:

~~~text
Interaction {
  source_row: int64,
  user_external_id: string,
  item_external_id: string,
  rating: float32,
  timestamp_utc: int64
}
~~~

Очистка:

1. Проверить обязательные ID, допустимый рейтинг и timestamp.
2. Упорядочить по timestamp и исходному номеру строки.
3. Для каждой пары user-item оставить первый отзыв. Поздняя оценка не заменяет прошлую.
4. Разбить события по глобальным временным границам.
5. На train итеративно удалять пользователей и товары с числом взаимодействий меньше 5 до устойчивого состояния.
6. Заморозить множества U* и I*. Применить их к validation/test; не вычислять core заново по будущему.
7. Присвоить внутренние ID по лексикографическому порядку внешних ID; сохранить mappings и их hashes.

Полный исходный датасет используется для контроля отбора, но модели обучаются на одной и той же выбранной совокупности событий. Истории за пределами выбранной совокупности не добавляются только отдельным моделям.

В аудите удалено 41966 повторных user-item строк; это не обязательно побайтовые дубликаты. Недопустимых строк по текущим проверкам не обнаружено.

Metadata join левый. Отсутствующий бренд/название не является причиной удалить взаимодействие: в отчёте остаётся ASIN. Это сохраняет проверенные размеры benchmark.

## 4. Временной протокол

Один пользователь получает top-10 в момент T по истории строго до T. Затем рекомендации сопоставляются с новыми положительно оценёнными товарами следующего периода.

Границы выбраны по 80-му и 90-му процентилям времени дедуплицированной полной категории, до отбора активной аудитории. Все события одного UTC-дня принадлежат одному периоду. После отбора пропорция 80/10/10 не сохраняется; это ожидаемо и отражено в числах.

| Назначение | Интервал UTC |
|---|---|
| Train | t < 2017-04-17 00:00:00 |
| Validation | 2017-04-17 00:00:00 <= t < 2017-12-08 00:00:00 |
| Test | t >= 2017-12-08 00:00:00, до конца доступных данных |

Последний наблюдаемый день исходного файла: 2018-10-04. Это задача snapshot-рекомендаций на длинный holdout-период, не предсказание следующего клика и не утверждение о современной покупательской активности.

Глобальные границы сохраняют временной порядок между пользователями. Per-user leave-last может позволять модели использовать более поздние события других пользователей при оценке раннего тестового события. Этот риск исследован в [A Critical Study on Data Leakage](https://arxiv.org/abs/2010.11060); чувствительность результатов к разбиению также рассматривает [Time to Split](https://arxiv.org/abs/2507.16289).

Порядок эксперимента:

1. Зафиксировать даты, cohort, label definition и ranges до обучения.
2. Настроить модели на train; оценивать validation на T_val.
3. Заморозить гиперпараметры и правило выбора числа эпох.
4. Переобучить финальные модели на train + validation из той же U*/I*.
5. Оценить test на T_test; события test не обновляют history или параметры.

Все кандидаты одного запроса оцениваются на одном T. Timestamp будущего целевого отзыва никогда не передаётся scorer как время рекомендации.

## 5. Каталог, релевантность и аудит отбора

I* содержит 7329 товаров, выбранных по train. В refit каталог не расширяется. Поэтому каждый объект основного benchmark уже имеет прошлую историю.

Для пользователя u:

~~~text
H_u(T) = все объекты с отзывом пользователя до T, независимо от оценки
C_u(T) = I* \ H_u(T)
R_u = новые объекты из C_u(T), оценённые >= 4 в holdout-периоде
~~~

Основная таблица рассчитывается на одном списке пользователей с непустым R_u для всех методов. Пользователь не исключается из-за плохих предсказаний, пустой положительной истории или ошибки конкретной модели.

У 35 train-пользователей нет оценок >= 4. Для ItemKNN/EASE заранее предусмотрен детерминированный MostPopular fallback при полностью неинформативном векторе оценок. Изолированные равенства разрешаются по item_id. Частота fallback публикуется по каждой модели.

Отбор сохраняет около 3,76% событий исходного validation и 2,55% исходного test. Основные выводы относятся к активным пользователям и товарам выбранного каталога. Они не описывают качество на всех 903330 пользователях исходной категории.

Различаем:

- неизвестный до cutoff пользователь/объект;
- известный, но не вошедший в train-only core;
- выбранный пользователь без положительного holdout;
- выбранный пользователь с положительными отзывами только вне I*.

Обязательно публикуем таблицу исключений и долю положительных событий выбранных пользователей, покрываемую I*. Дополнительный Recall_all_future считает попадания с полным числом будущих положительных отзывов выбранного пользователя в знаменателе, включая товары вне I*. Пользователь с такими отзывами, но без достижимой цели, получает 0 в этой диагностике. Это отдельная оценка покрытия, не основной warm-catalog Recall@10.

Уже измеренный предел покрытия выбранного каталога:

| Среди выбранных U*, до ограничения каталога | Validation | Test |
|---|---:|---:|
| Все будущие положительные отзывы | 7707 | 5393 |
| Положительные отзывы о товарах I* | 4710 | 3094 |
| Доля позитивных событий в I* | 61,11% | 57,37% |
| Пользователи с позитивами только вне I* | 797 | 791 |

Это micro-доля событий, а не значение Recall@10 модели. Основная macro-метрика по пользователям и эта доля показываются отдельно.

Amazon содержит выбранные пользователями отзывы, а не полный журнал показов. Ненаблюдённые объекты не являются доказанными отрицательными предпочтениями. Offline-метрики не интерпретируются как прирост CTR, продаж или удовлетворённости.

Решения о знаменателях, фильтрах и пустых рекомендациях могут менять выводы сравнения; поэтому они являются частью версионируемого протокола. [Offline evaluation options](https://doi.org/10.1007/s10791-020-09371-3).

## 6. Архитектура

~~~mermaid
flowchart LR
    A[Official CSV and metadata] --> B[Immutable raw files and SHA256]
    B --> C[Clean and temporal split]
    C --> D[Train-only cohort and ID mappings]
    D --> E[FitSnapshot and FeatureStore]
~~~

FeatureStore здесь означает небольшой локальный модуль с файлами и функциями, а не отдельный сервис.

Компоненты:

| Компонент | Ответственность | Выход |
|---|---|---|
| Downloader | Проверка источника и целостности | Raw файлы, manifest |
| DatasetBuilder | Очистка, split, core, mappings | События и cohort manifest |
| SnapshotBuilder | История на конкретный cutoff | Ratings COO, positive CSR, seen CSR |
| FeatureBuilder | Только доступные в прошлом признаки | Sparse features, statistics, schema |
| Model | Собственные fit и score | Веса и служебный model manifest |
| RecommendationEngine | Маски, fallback, tie-break, top-k | Top-10 по каждому пользователю |
| Evaluator | Общие метрики и диагностики | Per-user CSV, aggregate JSON |
| ExperimentRunner | Подбор, seeds, resume, refit | Trial logs и финальные runs |
| ReportBuilder | Таблицы, графики и примеры | Markdown/HTML и PNG |

Контракт модели:

~~~python
fit(snapshot, config, seed) -> ModelArtifact
score_users(user_ids, item_ids, as_of) -> scores[user, item]
save(path)
load(path)
~~~

FitSnapshot не содержит test labels. FeatureBuilder получает cutoff явно и проверяет, что source_timestamp каждого исторического агрегата меньше cutoff/времени обучающего примера.

Модель самостоятельно реализует score; общий RecommendationEngine одинаково превращает оценки всех моделей в рекомендации. Никакая модель не использует отдельную скрытую фильтрацию кандидатов.

Основные артефакты:

~~~text
dataset_manifest.json: sources, hashes, cleaning rules, boundaries, counts
cohort_manifest.json: selected IDs/hashes, exclusion statistics
features_manifest.json: schema, training cutoff, fitted transformations
run_manifest.json: model, config, seed, data hashes, environment, git revision
model.npz / weights.pt: learned parameters
recommendations.csv: run_id, anonymized_user_id, item_id, rank, score
metrics_per_user.csv: user_id, metric values, relevant_count, fallback flag
metrics.json: macro metrics, runtime, memory, coverage
~~~

Этапы идемпотентны: ключ кэша зависит от hashes входов, конфигурации, версии алгоритма и окружения. Незавершённый артефакт не считается успешным run. Неверные shapes, NaN/Inf и несовместимые mappings завершают запуск с ошибкой; такие trials остаются в журнале.

## 7. Модели и собственные реализации

Обозначения: Ω содержит наблюдаемые оценки текущего fit-периода; X_ui = 1[r_ui >= 4]; μ является средним рейтингом только fit-данных.

### 7.1 ItemKNN

Для ni положительных пользователей объекта i и nij общих положительных пользователей:

~~~text
s_ij = nij / sqrt(ni * nj) * nij / (nij + gamma), i != j
s_ii = 0
score_u = X_u W
~~~

Для каждого столбца j сохраняем k наиболее сильных входящих связей i -> j. Сходства, сглаживание, отбор соседей и score реализуются самостоятельно на SciPy sparse/NumPy. gamma и k подбираются на validation. Сглаживание является проектным выбором. [Первичная работа по item-based CF](https://www.ra.ethz.ch/CDstore/www10/papers/519/).

Если nij = 0 или ni * nj = 0, задаём s_ij = 0 без деления. Это также устраняет неопределённость при gamma = 0. Core построен по всем рейтингам, поэтому наличие положительных оценок у каждого товара не предполагается.

### 7.2 Explicit ALS

~~~text
r_hat_ui = mu + b_u + b_i + p_u^T q_i
L = sum_Omega (r_ui - r_hat_ui)^2
    + lambda_f * (||P||_F^2 + ||Q||_F^2)
    + lambda_b * (||b_users||^2 + ||b_items||^2)
~~~

У пользователя совместно обновляются b_u и p_u решением ridge-задачи при фиксированных объектах; затем симметрично обновляются объекты. Пропуски не включаются в loss. μ фиксируется после расчёта на fit-данных.

Для z_i = [1; q_i]:

~~~text
[b_u; p_u] = solve(sum_i z_i z_i^T + diag(lambda_b, lambda_f, ...),
                   sum_i z_i * (r_ui - mu - b_i))
~~~

Разрешённые библиотечные операции: матричные произведения и solve/Cholesky. Обучаемый алгоритм собираем сами. Не инвертируем маленькую матрицу явно для каждого пользователя. [Матричная факторизация и ALS](https://gwern.net/doc/ai/tabular/2009-koren.pdf), [SciPy Cholesky](https://docs.scipy.org/doc/scipy/reference/generated/scipy.linalg.cho_factor.html).

### 7.3 EASE

~~~text
min_B ||X - X B||_F^2 + lambda * ||B||_F^2, diag(B) = 0
P = (X^T X + lambda I)^(-1)
B_ij = -P_ij / P_jj for i != j; B_ii = 0
score_u = X_u B
~~~

Используем float64 и положительную lambda. Решение вычисляем Cholesky + solve; при необходимости по блокам столбцов единичной матрицы. Нормирование выполняется по диагональному элементу соответствующего столбца. Отрицательные коэффициенты сохраняются. EASE выбран за простую проверяемую формулу и посильный размер нашего каталога. [Статья EASE](https://arxiv.org/abs/1905.03375).

### 7.4 Factorization Machine

~~~text
f(x) = w0 + sum_j w_j x_j
       + 0.5 * sum_f [(sum_j v_jf x_j)^2 - sum_j v_jf^2 x_j^2]
~~~

Самостоятельная формула второго порядка, MSE по наблюдаемым оценкам и явный L2-штраф. PyTorch используется для autograd и оптимизатора. ID-only версия служит абляцией, но не заменяет обязательную FM с метапризнаками.

Вычисление взаимодействий занимает O(k * nnz(x)). Для full-catalog scoring признаки разделяем на группу user/context и группу item: сумма сводится к user-only scalar + item-only scalar + скалярному произведению агрегированных векторов. Это позволяет оценивать весь каталог батчами без создания десятков миллионов feature rows. Проверяем равенство ускоренного и прямого score на тестовых данных. [Авторские материалы FM](https://www.libfm.org/).

### 7.5 timeSVD++ с причинной историей

~~~text
d_u(t) = sign(t - mean_time_u) * abs(t - mean_time_u)^beta
h_u(t) = sum_{j in H_u(<t)} y_j / sqrt(|H_u(<t)|)

r_hat_ui(t) =
  mu + b_i + b_i,bin(t)
  + b_u + alpha_u * d_u(t) + b_u,day(t)
  + q_i^T [p_u + a_u * d_u(t) + p_u,day(t) + h_u(t)]
~~~

При пустой истории h = 0. Есть временной item bias, дрейф пользовательского bias/вектора и дневные поправки. Обучение MSE с отдельной регуляризацией постоянных и временных параметров. mean_time_u вычисляется по fit-данным; время измеряется в днях UTC, beta изначально 0.4.

В отличие от полного train-набора истории в исходной постановке, H_u(<t) содержит только более ранние дни. Это явно обозначенная causal adaptation timeSVD++, а не буквальная реплика Netflix-эксперимента. Неизвестные дневные поправки и отсутствующие item-time bins дают 0; глобальные bias и дрейф продолжают работать. Правило не меняется по test. [Koren, временные компоненты](https://cseweb.ucsd.edu/classes/fa17/cse291-b/reading/p447-koren.pdf).

Чтобы не раздувать prefix-history, группируем события по пользователю и дню, суммируем y_j по дням и используем сдвинутую cumulative sum. Блоки пользователя обрабатываются целиком или с точным сохранением префикса. Обработка должна сохранять градиент к history embeddings; detached cache внутри эпохи не используется как незаметная замена objective.

Абляция без временных параметров, но с той же implicit history, отделяет вклад времени от вклада SVD++. Победа timeSVD++ не предполагается заранее: короткие истории могут не поддерживать сложные временные параметры.

### Общие правила

- KNN/EASE используют бинарные положительные истории; ALS/FM/timeSVD++ используют все наблюдаемые рейтинги. Это общий evaluation protocol, но разные обучающие цели.
- Missing ratings не объявляются отрицательными оценками для rating-моделей.
- Предсказания рейтингов не обрезаются до [1,5] перед ranking: иначе образуются искусственные ties.
- Готовые recommender implementations, sklearn ElasticNet, implicit, Surprise, libFM и готовые модели фреймворков не применяются.
- Вспомогательные операции linear algebra, sparse tensors, autograd и библиотеки поиска гиперпараметров допустимы.

## 8. Метапризнаки FM без информации из будущего

Основная FM использует признаки, происхождение которых можно проверить по timestamp:

| Признак | Как вычисляется | Доступность |
|---|---|---|
| user_id, item_id | Mapping текущего benchmark | Train |
| log(1 + prior_user_reviews) | Число прошлых отзывов пользователя | До t |
| prior_user_mean_rating | Средняя прошлая оценка пользователя | До t |
| log(1 + prior_item_reviews) | Число прошлых отзывов товара | До t |
| prior_item_mean_rating | Средняя прошлая оценка товара | До t |
| item_age_days | Дни после первого наблюдавшегося отзыва | До t |
| user_tenure_days | Дни после первого наблюдавшегося отзыва пользователя | До t |
| month/day-of-week | Календарь момента запроса | В момент t |

Первые наблюдения получают count=0, средний рейтинг=3 как заранее заданный нейтральный prior, age=0. Первый отзыв не называется датой выхода товара. Числовые преобразования и масштабирование обучаются только на fit.

При подготовке обучающих строк все события одного дня сначала получают признаки по предыдущим дням и только затем обновляют состояние агрегаторов. Текущая оценка не участвует в собственном mean. В validation/test признаки строятся один раз по fit-истории на соответствующем snapshot cutoff.

Это метапризнаки пользователя, объекта и контекста взаимодействия; модель не ограничивается парой ID.

Название, категории и бренд из каталожного snapshot используем в основном отчёте для подписей. Дополнительная FM с brand/category разрешена как отдельная абляция с явным допущением их стабильности. Основной результат от этого допущения не зависит.

Исключены price at crawl time, salesRank, глобальный средний рейтинг, helpful votes, also_buy/also_view, текст целевого отзыва и статистики из test. Официальная документация не даёт полную историческую версию каталога; поздние метаданные нельзя выдавать за известные во время старого взаимодействия. [Описание полей Amazon](https://cseweb.ucsd.edu/~jmcauley/datasets/amazon_v2/).

## 9. Оценка и сравнение

Основная модель выбирается по macro NDCG@10. Дополнительно публикуются Recall@10, Precision@10 и MAP@10, а для rating-моделей RMSE как диагностическая метрика.

~~~text
Recall_u@10 = hits_u / |R_u|
Precision_u@10 = hits_u / 10
DCG_u@10 = sum_{k=1..10} rel_u(k) / log2(k + 1)
IDCG_u@10 = sum_{k=1..min(10, |R_u|)} 1 / log2(k + 1)
AP_u@10 = sum_{k=1..10} Precision_u@k * rel_u(k) / min(10, |R_u|)
~~~

Для основной таблицы R_u непустое. Если кандидатов меньше 10, пустые позиции имеют нулевую релевантность; знаменатель Precision остаётся 10. Сначала метрика рассчитывается для каждого пользователя, затем берётся среднее с равным весом пользователей.

Оценивается полный C_u. Случайные 100 негативов для оценки не используются: сэмплированные ranking metrics способны менять относительный порядок методов. [On Sampled Metrics for Item Recommendation](https://research.google/pubs/on-sampled-metrics-for-item-recommendation/).

Порядок результата: score по убыванию, затем стабильный item_id по возрастанию. Для данного каталога допустима стабильная сортировка строки целиком; если применяется argpartition, ties на границе top-10 разрешаются явно, иначе reproducibility нарушится.

Дополнительные показатели:

- CatalogCoverage@10: доля I*, встречающаяся в рекомендациях.
- Средняя train-популярность рекомендованных объектов.
- Межпользовательское совпадение списков.
- Доля fallback и пользователей без информативного персонального сигнала.
- Время fit, время формирования рекомендаций, размер artifact, peak RSS.
- Ошибки по заранее заданным корзинам train-активности.

Примеры top-10 выбираются по фиксированному seed и корзинам активности до просмотра качества моделей. В отчёте показываются заголовки объектов, прошлые оценки пользователя, рекомендации и будущая релевантность. Исходный reviewerID заменяется внутренним ID.

## 10. Подбор гиперпараметров и повторные прогоны

До обучения фиксируем ranges, sampler seed и бюджет. Хорошо настроенные простые baseline необходимы для содержательного сравнения, что показывает [анализ воспроизводимости рекомендаций](https://arxiv.org/abs/1911.07698).

Зафиксированный бюджет основного эксперимента:

| Метод | Пространство поиска | Бюджет |
|---|---|---|
| ItemKNN | k: 20, 50, 100, 200; gamma: 0, 10, 50, 100 | 16 конфигураций |
| EASE | lambda: 1, 3, 10, 30, 100, 300, 1000, 3000 | 8 конфигураций |
| ALS | rank: 16/32/64; lambda_f, lambda_b log-scale; до 40 итераций | Опорный набор + 15 фиксированных random trials |
| FM | rank: 16/32/64; learning rate и L2 log-scale; до 50 эпох | Опорный набор + 15 фиксированных random trials |
| timeSVD++ | rank: 16/32/64; learning rate, L2 и temporal L2; bin: 30/90 дней | Опорный набор + 15 фиксированных random trials |

Планируемые диапазоны lambda для ALS: [0.01, 100] при ненормированном sum-loss. Для PyTorch-моделей mean-MSE + отдельно определённый mean-square penalty; L2 [1e-6, 1e-1], learning rate [1e-4, 1e-2]. Код обязан явно фиксировать нормировку loss и штрафов; одинаковое название lambda не означает одинаковое значение между методами.

Для FM/timeSVD++ максимум 50 эпох, patience=5 validation-проверок. Temporal penalty не слабее выбранного base penalty. Конкретные draws сохраняются до первого trial; ошибки и OOM остаются в trial log. Test не используется для расширения ranges.

Фактические draws находятся в configs/benchmark.json, генератор использует random.Random(2026). Размер minibatch FM/timeSVD++ равен 4096 событий; timeSVD++ сохраняет полные пользовательские истории. Размер выбран по pilot wall time до основного поиска. Признаки возраста логарифмируются log(1+days). Абляции используют выбранные параметры родительской модели и отдельный validation early stopping, без самостоятельного полного поиска параметров.

После выбора конфигураций:

- ALS/FM/timeSVD++ повторяются с seeds 17, 42, 2026.
- ItemKNN/EASE выполняются один раз при фиксированном окружении.
- При каждом финальном seed число эпох определяется на validation; refit использует выбранное число эпох, без early stopping на test.
- Основная таблица показывает mean и std по seeds.
- 95% интервалы для парных различий строятся paired bootstrap по пользователям, 2000 повторов, bootstrap seed=2026.

При bootstrap сначала усредняем user-level scores по seeds, затем ресэмплируем одинаковых пользователей для обоих методов. Seed-прогоны не считаются независимыми пользователями.

Основной заранее заданный contrast: timeSVD++ против ALS. Разницу объясняем с помощью абляции SVD++ без времени; само сравнение ALS/timeSVD++ не выделяет чистый эффект времени. Остальные парные сравнения считаются исследовательскими.

## 11. Производительность и ограничения

После аудита каталог содержит 7329 объектов. Одна плотная float64 матрица EASE занимает около 0,400 GiB. Gram, Cholesky, решение и рабочая память требуют нескольких таких буферов. Модели запускаются последовательно; EASE не обучается одновременно с другими memory-heavy trials.

Память матрицы всех пользовательских scores не выделяется. Батч пользователей, например 128, оценивает 7329 кандидатов, после чего сохраняются только top-10 и per-user metrics. Размер батча является параметром исполнения, а не способом уменьшить каталог.

Факторы ALS/FM/timeSVD++ имеют низкую размерность; разреженные истории хранятся CSR/CSC. Для temporal embeddings создаются только наблюдавшиеся пары user-day/item-bin. При inference неизвестные пары не получают случайно инициализированных параметров.

Перед полным search выполняется pilot одного trial каждого метода. Записываются wall time, peak RSS, число потоков BLAS, CPU/GPU и размер данных. Реальные сроки обучения оцениваются после pilot; дизайн не обещает фиксированное время на неизвестном компьютере.

Ускорения допускаются только после сравнения с простой эталонной реализацией. В частности, полное EASE не заменяется незаметно top-k sparse approximation, а FM не теряет взаимодействия при разделении признаков на группы.

## 12. Воспроизводимость и GitHub

Предлагаемый стек: Python, NumPy, SciPy, pandas, PyTorch, matplotlib, pytest; Optuna допустима только как orchestration поиска. Точные версии и Python runtime фиксируются lock-файлом после проверки совместимости. Основной запуск CPU; отдельный GPU-run не смешивается с CPU timing.

Для каждого run сохраняются git revision и признак dirty tree, hash конфигурации, seed всех генераторов, versions Python/NumPy/SciPy/PyTorch/BLAS, число потоков и устройство. PyTorch включает deterministic algorithms там, где это поддерживается; недетерминированная операция должна быть видна, а не тихо проигнорирована. [Документация PyTorch](https://docs.pytorch.org/docs/main/generated/torch.use_deterministic_algorithms.html).

Одинаковый seed не обещает побитового совпадения между разными версиями библиотек или CPU/GPU. Контракт: повторяемые артефакты данных и сопоставимые метрики в зафиксированном окружении; численные допуски проверяются тестами.

Каждая команда принимает путь к config и output directory. Повторный reproduce использует только валидные совместимые артефакты и проверяет manifest.

CI проверяет небольшие синтетические данные и математические инварианты. Полный dataset download и многократное обучение не запускаются на каждом pull request. Полный benchmark является отдельным явным запуском. Кэш зависимостей лишь ускоряет установку; отсутствие кэша не мешает воспроизведению. [GitHub Actions caching](https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching).

Лицензия кода не распространяется автоматически на исходные данные. Репозиторий содержит ссылки на первоисточник, citation и download manifest; raw CSV, тексты отзывов и имена пользователей не публикуются. Условия использования данных проверяются перед подготовкой публичного релиза.

## 13. Проверки, которые нужны до доверия метрикам

1. Очистка: первый отзыв пары не заменяется поздним; повторный запуск даёт те же hashes.
2. Время: ни один train timestamp не достигает cutoff; события одного дня не пересекают split.
3. Cohort: добавление новых holdout-строк не меняет train-core и train features при фиксированных датах.
4. Исторические признаки: изменение будущей оценки не меняет признаки прошлых строк.
5. KNN: нулевая диагональ, ручной пример сходства, правильная ориентация top-k связей.
6. ALS: один полный блоковый шаг не увеличивает объявленный objective сверх допуска.
7. EASE: нулевая диагональ, формула по столбцам, решение удовлетворяет условиям оптимальности на маленькой матрице.
8. FM: быстрая формула совпадает с явным перебором пар; градиенты проходят finite-difference/gradcheck на маленьком примере.
9. timeSVD++: выключенные temporal components дают SVD++; неизвестный день даёт нулевую дневную поправку; target не входит в свой history-prefix.
10. Ranking: ровно 10 уникальных допустимых товаров, seen исключены, tie-break стабилен, пустой персональный сигнал не удаляет пользователя.
11. Метрики: ручные списки с известными Precision/Recall/AP/NDCG, одинаковый cohort для всех моделей.
12. Артефакты: load/save сохраняет scores; неверный mapping/cutoff/hash обнаруживается.
13. Происхождение: запрещённые готовые обучаемые модели не входят в imports и dependencies.
